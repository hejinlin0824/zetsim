# zetsim Windows 实机验收提示词（可直接交给测试同事）

你是负责 zetsim 项目的 Windows 实机验收人员。请像真实使用者一样启动服务、打开浏览器、操作案例库和 C 项目工作台，并运行自动化测试。目标不是证明“页面能打开”，而是检查教程是否能跟着做、六个案例是否能完成、编辑/编译/运行链路是否可靠，以及混合仿真的数值与性能表现。

## 一、必须遵守的验收规则

1. 只测试，不修代码、不新增提交、不推送、不合并分支。不要切换或修改 main，不要修改 tag。
2. 只在 DEV 分支验收。记录完整的 40 位提交 SHA；报告里不能只写短 SHA。
3. 开始前先检查分支和工作区。如果不是 DEV，或 git status --short 有任何已有改动，先停下并报告，不要擅自覆盖、清理或还原别人的文件。
4. 不允许执行会丢失工作成果的清理命令，例如 git reset --hard 或 git clean -fd。测试临时改动必须逐文件保存并确认恢复，不能用大范围清理代替。
5. 不能把 GitHub Actions 通过当作 Windows 浏览器实测通过；不能把“编译成功”当作“功能正确”；不能把一张截图当作完整验收。
6. 遇到失败时先保存证据、复现步骤和日志，不要当场猜测原因或修代码。
7. 所有性能结果必须同时报告墙钟时间和仿真时间；如果波形还没填满观察窗，要明确写出，不能把空波形判定为正确。

## 二、验收开始前：记录环境与版本

在仓库根目录打开 PowerShell，执行：

    git branch --show-current
    git rev-parse HEAD
    git status --short
    python --version
    python -c "import sys; print(sys.executable)"
    python -m pip show zetsim

确认当前分支为 DEV，工作区干净。记录 Windows 版本、Python 版本、浏览器名称和版本、屏幕缩放/DPI（若 UI 有错位），以及当前提交 SHA。

然后同步最新 DEV：

    git fetch origin
    git switch DEV
    git pull --ff-only origin DEV
    git rev-parse HEAD
    git status --short

如果起初工作区不干净，不要拉取覆盖；先报告并由负责人处理。不要直接套用以上同步命令来覆盖本地工作。

## 三、环境与自动化测试

如果依赖尚未安装，按项目的虚拟环境规范安装。推荐命令如下：

    python -m pip install -e ".[dev]"
    python -m pytest tests/ -q

如果已在项目 venv 中，请确保 python -m pytest 用的就是运行服务的那个解释器。保存完整测试输出，报告通过数、失败数、跳过数和失败用例名。任何失败都要保留完整 traceback。

如已安装 ARM GNU 工具链，逐一构建六个 C 项目：

    python -m zetsim build projects/gpio_blink
    python -m zetsim build projects/led_marquee
    python -m zetsim build projects/exti_button
    python -m zetsim build projects/uart_echo
    python -m zetsim build projects/pwm_adc_control
    python -m zetsim build projects/pwm_rc_filter

记录每个项目的编译/链接结果和产物路径。若工具链缺失，单独标记“环境阻塞”，不要把它误写成代码失败，也不要跳过其余可执行测试。

## 四、浏览器实测：启动与基本操作

启动服务并保留终端日志：

    python -m zetsim serve

打开 http://127.0.0.1:8000。若默认端口被占用，选择可用端口并记录。打开开发者工具 Console 和 Network。

检查以下内容：
- 页面能否完整加载，画布和左右面板是否正常显示。
- 默认原理图是否出现 MCU、电源/地、LED、按键、电位器和探针等元件。
- 运行、暂停、复位和加载固件操作是否生效。
- 是否出现未捕获 JavaScript 错误、持续重复请求、HTTP 4xx/5xx。
- 在浏览器刷新后，原理图是否按产品预期恢复；若状态不同，记录刷新前后差别。
- 画布缩放、移动元件、添加/删除导线和窗口大小变化时，交互坐标是否正确，没有明显错位或画布空白。

不需要测试真实 STM32 硬件；本轮目标是运行在 Windows 上的 zetsim 软件。如果你额外接了实体硬件，请把它作为单独的扩展测试报告，不能与软件仿真结果混在一起。

## 五、案例库和教程可学性测试

按 docs/learning-path.md 的顺序至少完成 GPIO、跑马灯、EXTI、USART、PWM+ADC、RC 六个案例。不要直接猜界面；要根据教程定位 C 源文件、执行操作，并判断一个初学者能否按说明复现。

对每个案例检查：
- 案例详情里的学习目标、推荐接线、源码阅读位置、动手任务和完成条件是否齐全。
- “载入推荐电路”后，元件与连线是否确实符合该案例需要。
- 教程提到的文件路径、函数名、寄存器和预期现象是否与当前 DEV 源码一致。
- 任务勾选、案例完成数量和进度条是否立即更新；刷新同一浏览器后进度是否保留。
- 进度是否只保存在当前浏览器；不要误认为它会自动同步至 GitHub 或另一台电脑。
- 遇到教程文字无法完成、源文件名不存在、UI 按钮失效或验收标准不明确时，记录精确章节、操作和截图。

学习性测试请特别区分两种问题：教程说明不清是文档可用性问题；按照教程操作但功能不符合预期才是产品功能问题。

## 六、C 项目工作台：保存、编译、运行与防误操作

在项目菜单中逐个选择项目，重点验收 gpio_blink 和 led_marquee，再抽查其他项目。

检查：
1. 选择项目后显示正确的 main.c，文件内容与仓库对应文件一致。
2. 编辑器行号与源码行数对齐，长文件滚动时不明显漂移。
3. 做一个可恢复的临时小改动，确认“未保存”状态出现。
4. 使用 Ctrl+S 后，确认保存成功、未保存状态消失。
5. 使用 Ctrl+Enter 后，确认先保存再编译；成功时加载新固件，失败时保留错误日志并指出文件名/行号。
6. 在未保存状态切换项目，确认系统会提示保存、放弃或取消；不能静默地把当前文件写入另一个项目。
7. 在编译失败后重新修正并编译，确认旧错误信息不会造成误判。
8. 检查输出文件是否写到当前项目对应目录，而不是另一个工程目录。

安全要求：临时改动前确认工作区干净并备份原文件内容。测试结束后恢复原内容，运行 git diff 和 git status --short 验证没有留下测试改动。若恢复时发现内容与备份不一致，立刻停止，不要自动覆盖。

## 七、功能案例验收标准

### A. GPIO 闪灯

- 打开 projects/gpio_blink 项目，确认 main.c 中存在 BLINK_MS 参数。
- 如需修改闪烁速度，把临时修改限制在该文件，并在测试后恢复原值。
- 确认 LED 的实际状态连续翻转，PA5 探针有对应变化。
- 报告翻转间隔的观测值，不要把“亮灭完整周期”和“单次翻转间隔”混为一谈。

### B. 8 路 LED 跑马灯

- 载入 8-LED 跑马灯电路。
- 确认 PA0–PA7 对应八路 LED，且各路有独立串联限流电阻。
- 编译运行 led_marquee，确认灯按顺序移动，STEP_MS 改变后速度发生变化。
- 执行布线检查；记录任何错误或警告。若报告无限流电阻，核实原理图是否真的缺少电阻，不要仅为让报告通过而忽略它。

### C. EXTI 按键

- 编译运行 exti_button。
- 对 SW1 进行五次完整按下/松开，记录 LED 实际翻转次数。
- 复位再试一次，确认不会因残留状态而不能再次触发。
- 若失败，记录是按键没有改变输入、EXTI 没触发、固件 handler 没运行，还是 LED 没响应；不要笼统写“中断坏了”。

### D. USART1 回显

- 编译运行 uart_echo。
- 确认启动问候语出现。
- 分别输入单字符、hello 和一段至少 20 字符的文本，确认收到相同回显且没有明显丢字或乱码。
- 报告终端使用的 USART 编号和固件项目名。

### E. ADC → PWM

- 编译运行 pwm_adc_control。
- 确认 PA0 的 PWM 频率约为 10kHz。
- 缓慢调整电位器，检查输入电压变化时占空比是否随之变化。
- 分别记录低、中、高三个输入位置的电压、频率、占空比。若无法自动读占空比，记录示波器读数与波形截图。

### F. RC 纯电路与 RC + LED

使用相同参数进行对比，不要中途更换电路或观测窗口：

- PWM：10kHz、约 30% duty、3.3V 高电平。
- 电阻：1kΩ。
- 电容：100nF。
- 时间常数理论值：τ = R × C = 100µs。
- 纯 RC 的理想平均输出电压约 0.99V。
- 之前验收观测到的参考波形为平均值约 0.99V、纹波约 0.69–1.33V；这些是对照参考而不是允许不检查其他条件的硬性精度保证。

分两组测量：
1. 纯 RC：不接 LED。
2. RC + LED：其余参数、PWM、探针位置和测量时长保持一致，仅增加 LED。

每组都先让仿真运行，再记录：
- 测试墙钟开始/结束时间，墙钟总秒数。
- 开始和结束时显示的 t_ms，仿真时间增量。
- 仿真时间实时率 = 仿真时间增量 ÷ 墙钟秒数 ÷ 1000。结果可以用百分比报告。
- 稳态窗口内的平均电压、最小值、最大值和纹波。
- 波形历史点数量；若历史未填满窗口或读到全 0，应明确标为“观察窗数据不足”，不能据此断言电路数值是 0。
- 浏览器是否卡顿，/api/state 等请求是否异常缓慢，Console 是否出现错误。

同时用同一固件做无电容基线：gpio_blink 的 LED 翻转和 t_ms 应接近实时；若其速度明显退化，记录为回归。纯 RC 与 RC+LED 的性能必须分开报告，因为它们可能走不同求解路径。

性能报告要同时保留“数值是否正确”和“跑得有多快”两列。即使波形数值符合预期，实时率仍然可能不合格；反之，单纯提高实时率也不能接受波形明显失真。
